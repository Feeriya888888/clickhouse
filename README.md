# ClickHouse: аналитика интернет-магазина

проект: аналитическое хранилище на ClickHouse для e-commerce,
от генерации данных до продакшен-приёмов проектирования схемы.

## Задача

Спроектировать и развёрнуть хранилище событий и заказов интернет-магазина
и ответить на продуктовые вопросы:

- сколько уникальных пользователей приходят каждый день (DAU);
- как выглядит воронка конверсии от просмотра товара до покупки;
- удерживаются ли пользователи по неделям после регистрации (когортный retention);
- какие товары и категории приносят выручку;
- как выручка распределяется по городам и каналам трафика.

## Стек

- **ClickHouse 24.8** (Docker) — хранилище и OLAP-движок
- **Python 3.9+** (только стандартная библиотека) — генерация и загрузка данных
- **SQL** — схема и аналитические запросы

## Структура проекта

```
│   ├── generate_data.py    # генератор синтетических данных (~2 млн событий)

    └── sample_events.csv   # пример сгенерированных событий
```



## Проектные решения 

**Партиционирование по месяцам** (`PARTITION BY toYYYYMM`) — почти все запросы
режут данные по диапазону дат, так ClickHouse не сканирует лишние партиции.

**ORDER BY под реальные запросы** — ключ сортировки `(event_time, user_id)`
ускоряет выборки по датам и фильтрацию по пользователю.

**TTL 24 месяца** — события устаревают, ClickHouse вычищает их автоматически,
объём хранилища не растёт бесконечно.

**Enum8 вместо String** для типа события и устройства — 1 байт вместо десятков,
на миллиардах строк это существенно.

**LowCardinality(String)** для городов, категорий и источников трафика — словарное
кодирование, дешёвые GROUP BY.

**uniqExact vs uniq** — в проекте оба: точный подсчёт и HyperLogLog-приближение
(`uniq`), которое работает за O(log log N) памяти. В `queries.sql` запрос 6
сравнивает их на одних данных.

**Материализованное представление** (`dau_daily` на AggregatingMergeTree) —
предагрегация DAU на этапе вставки: дашборд читает компактную таблицу,
а не сканирует сотни миллионов событий.
